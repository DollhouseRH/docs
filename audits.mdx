## What the reviews actually found

The serious findings were real and are worth naming, because the fixes are what the contracts do now.

**The upgrade path forked the chain.** A successor deployment read the old head too early, so an upgrade could produce two competing chains. Fixed: a successor now adopts the trunk lazily, only after the old version has handed over and gone idle.

**A bad successor could freeze trading.** Unbounded gas in the handover meant a hostile successor could make every old swap revert. Fixed: fixed gas budgets, cached failures, queued fees that anyone can push along.

**Deep ancestor payouts were stranded.** The conversion arithmetic underflowed to zero around the tenth generation, which would have made roughly a third of deep-chain fees unpayable. Fixed: full-precision arithmetic walked link by link.

**Keepers could be overpaid after a crash.** Prices came from historical averages only, so a crashed pool still quoted its pre-crash price for half an hour. Fixed: every link is now priced at the lowest of spot, the 30-minute average and the 7-day average.

**A disclosure was simply false.** Our own documentation claimed a "non-refundable bond floor" for winners. There is none: winners get the whole bond back. The review called it out by name and the docs were corrected.

**A round could be settled but not scored after a delayed relay.** An independent diff review of the review-2 contract changes found that the score-history ring was sized for the wrong worst case, so a round whose random-end beacon arrived late could lose the far edge of its own scoring window. Fixed: the ring is now sized off the full settlement tail, including the deterministic-timeout path.

**Taking a spot in the chain is cheap.** This was measured, not fixed. It is disclosed on [Risks](/risks) and in [The chain](/the-chain).

**A keeper bug found only by running it live.** The first fully automated round-end run (run 7) found that the keeper's purse-ranking logic could re-send the same no-op transaction forever for a candidate that can never win a seat on a two-seat leaderboard. Fixed, with a hard budget and a daily gas cap added underneath so a future mistake in the same logic cannot become an unbounded spend again. That whole ranking path has since been removed: the purse is no longer contested, so there is one purse call per generation and nothing to rank.

**One dust swap could deny score submission for an entire round.** An automated audit report found that the score-history ring writes its slot once, on the first swap to touch it, so a small trade placed late in the round's final slot left no bracketing checkpoint and every candidate's score submission reverted for the whole window. Fixed with an exact-sample fallback, then hardened again in the next review round.

**The fix for that denial created a selection bug.** An independent diff review found that the exact-sample fallback let a trader choose which sample answered a round's end by placing trades after the bell, moving a score the random end was supposed to have fixed. Fixed by freezing checkpoint writes at the round's published end and sealing the first swap past it.

## What is still open

- **No paid third-party audit.** The plan is to circulate the code to independent Solidity engineers for a read, then run a full paid audit pipeline.
- **The vault was formally verified at review 4** (22 of 26 rules). Review 5 changed a small part of it: the re-denomination to the edge token and one delivery guard. Re-verifying that change hit a bug in the Prover itself, reported to the tool's vendor with a reproducer. The changed lines are instead covered by property tests, fuzzing, fork tests, 18 symbolic (Halmos) checks and four independent manual reviews of that diff. Formal re-verification of the vault resumes when the Prover is fixed. The round manager and the hook specifications were both re-verified at review 5, with the vault summarised rather than loaded: the round manager has 31 of 36 rules verified and the hook 17 of the 21 that ran. A handful of other rules remain unproved for reasons other than a code defect: a sub-wei rounding rule (SLV-03), the per-route fee count (FEE-01), whose per-pool half is now not expressible at this tier for a language limitation on the hook key type and falls back to fuzz and unit testing, and the purse-landing step, which needs a deployer-level specification. [certora/RESULTS-review-5.md](https://github.com/DollhouseMarkets/dollhouse/blob/main/certora/RESULTS-review-5.md). One latent contract finding turned up during that pass and has since been fixed: the round manager used to treat an empty head address as its once-only adoption flag, so adopting the zero address would have left the flag unset; it was unreachable on the deployed wiring (the factory constructor already refused such a token) and now carries its own dedicated flag regardless. Stated plainly: the class of defect only a prover excludes is a sequence-dependent accounting drift inside the vault's own ledgers, and its worst case is a mis-stated fee balance, not a drained pool, because no admin key exists and liquidity is locked.
- **A purse has never been deployed by the automated keeper under the uncontested rule on a live chain.** The older contested form was exercised manually (run 6); the keeper correctly declined to deploy on run 7 because there was nothing to deploy. Run 8 deployed the edge bid and two ancestor payouts, so the keeper path itself has fired.
- **The deterministic round-end fallback has never fired on any live run**: every round so far has settled through the verified random-beacon path.
- **The 7-day mainnet handover delay has only run at a 1-hour testnet-scaled delay**, and only on one build of the contracts; it has not been repeated on the current bytecode.
- **The 7-day slow price average has never fired on any live run**: every testnet pool has been hours old, never a full day.
- **Two contracts have needed multiple resubmissions to verify on the testnet explorer**, and every contract everywhere is a partial (not full) bytecode match, a build-setting choice that will change for the mainnet deployment.
- **Browser countdown clocks can drift from the chain's own clock**, and a couple of constants are shown from two places instead of one; both are known, open web findings.
- **The mainnet keeper-bounty floor has not been picked yet**: testnet used a scaled-down number.
- **A real wrong-chain wallet test** for the web app is still needed before beta.

## The honest position

Why this matters: traders should be able to check for themselves rather than take the project's word for it.

Trust here means the numbers are public, the findings are public, the mechanism cannot be changed after deploy, and nobody can withdraw your liquidity. It does not mean the code is proven correct. It is not.
